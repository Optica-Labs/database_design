# Adversarial AI Safety Database Design

## Overview

This database serves as the **single source of truth** for an adversarial AI safety system that tests client AI models and assesses the safety of their outputs. The system operates as an automated adversarial testing platform where:

1. **AI agents and ML models** are registered in the system
2. **Client models** are submitted for safety evaluation
3. **Adversarial test cases** are executed against client models
4. **Safety assessments** are performed on model outputs
5. **Alerts and compliance reports** track safety issues

## System Architecture

The database is designed to support the following workflow:

```
Client Model Registration
    ↓
Test Case Selection
    ↓
Adversarial Testing (executed by AI agents)
    ↓
Model Output Capture
    ↓
Safety Assessment (by evaluator agents)
    ↓
Alert Generation & Reporting
```

## Database Schema

### Core Entities

#### 1. `ai_agents`
Stores information about AI agents and ML models that operate within the system.

**Key Fields:**
- `agent_id`: Unique identifier
- `agent_type`: Type of agent (adversarial, evaluator, classifier, monitor)
- `model_architecture`: Underlying model (e.g., GPT-4, Claude)
- `capabilities`: JSON array of agent capabilities
- `status`: Current status (active, inactive, deprecated)

**Use Cases:**
- Track different AI agents performing tests and evaluations
- Version control for agent models
- Audit trail of which agent performed which action

#### 2. `client_models`
Stores information about client models being tested for safety.

**Key Fields:**
- `model_id`: Unique identifier
- `client_id`: Client who owns the model
- `model_name` & `model_version`: Model identification
- `endpoint_url`: API endpoint for testing
- `risk_level`: Current assessed risk (low, medium, high, critical)
- `status`: Registration status

**Use Cases:**
- Register new models for testing
- Track model versions and deployments
- Monitor risk levels over time

### Testing Framework

#### 3. `test_categories`
Defines categories of safety tests.

**Examples:**
- Jailbreak Attempts
- Toxicity & Hate Speech
- Bias Detection
- Prompt Injection
- Data Privacy

#### 4. `adversarial_test_cases`
Stores adversarial prompts and test cases.

**Key Fields:**
- `test_case_id`: Unique identifier
- `test_prompt`: The adversarial input to test
- `expected_behavior`: Description of safe behavior
- `attack_type`: Type of attack (jailbreak, prompt-injection, etc.)
- `severity`: Test severity level

**Use Cases:**
- Library of adversarial test cases
- Continuously evolving test suite
- Categorization by attack type and severity

### Execution & Results

#### 5. `test_executions`
Records each test execution against a client model.

**Key Fields:**
- `execution_id`: Unique identifier
- `model_id`: Model being tested
- `test_case_id`: Test being executed
- `executing_agent_id`: Agent performing the test
- `status`: Execution status (pending, running, completed, failed)

**Use Cases:**
- Track all test runs
- Monitor execution status
- Performance metrics (execution time)

#### 6. `model_outputs`
Stores outputs generated by client models during testing.

**Key Fields:**
- `output_id`: Unique identifier
- `execution_id`: Associated test execution
- `output_text`: The model's response
- `generation_time_ms`: Response time
- `temperature` & `other_parameters`: Model parameters used

**Use Cases:**
- Store complete model responses
- Analyze output characteristics
- Historical record for audits

### Safety Assessment

#### 7. `safety_assessments`
Stores safety evaluations of model outputs.

**Key Fields:**
- `assessment_id`: Unique identifier
- `output_id`: Output being assessed
- `evaluator_agent_id`: Agent performing evaluation
- `safety_score`: 0-100 score
- `is_safe`: Binary safe/unsafe flag
- `risk_level`: Assessed risk level
- `violation_types`: JSON array of detected violations
- `reasoning`: Explanation of assessment

**Use Cases:**
- Automated safety scoring
- Track which outputs are unsafe
- Provide reasoning for decisions

#### 8. `safety_metrics`
Stores detailed safety metrics for each assessment.

**Examples of Metrics:**
- Toxicity score
- Bias score
- Hallucination rate
- Refusal rate
- Coherence score

### Audit & Compliance

#### 9. `audit_logs`
Comprehensive audit trail of all system activities.

**Key Fields:**
- `event_type`: Type of event (model_registered, test_executed, etc.)
- `entity_type` & `entity_id`: What was affected
- `actor_type` & `actor_id`: Who performed the action
- `old_values` & `new_values`: Change tracking (JSON)
- `timestamp`: When it occurred

**Use Cases:**
- Complete audit trail
- Compliance reporting
- Security monitoring
- Change tracking

#### 10. `compliance_reports`
Stores periodic compliance and summary reports.

**Key Fields:**
- `report_type`: Type of report (daily_summary, model_audit, etc.)
- `total_tests`, `passed_tests`, `failed_tests`: Test statistics
- `critical_issues`, `high_issues`, etc.: Issue counts by severity
- `overall_safety_score`: Aggregate score
- `report_data`: Detailed JSON data

**Use Cases:**
- Regular compliance reporting
- Management dashboards
- Trend analysis

### Alerts & Notifications

#### 11. `safety_alerts`
Tracks safety alerts and incidents.

**Key Fields:**
- `alert_id`: Unique identifier
- `model_id`: Model that triggered alert
- `alert_type`: Type of alert (critical_failure, pattern_detected, etc.)
- `severity`: Alert severity
- `status`: Current status (open, investigating, resolved)
- `resolution_notes`: How it was resolved

**Use Cases:**
- Real-time incident tracking
- Alert management workflow
- Pattern detection

## Views

### `vw_latest_model_assessments`
Shows the most recent safety assessment for each model. Useful for quick status checks.

### `vw_model_safety_summary`
Provides aggregate safety statistics per model including:
- Total tests run
- Pass/fail counts
- Risk level distribution
- Average safety score

### `vw_active_alerts`
Shows all open safety alerts with full context, including:
- Model information
- Alert details
- Time since alert opened

## Common Use Cases

### Registering a New Model for Testing
```sql
INSERT INTO client_models (client_id, model_name, model_version, model_type, endpoint_url)
VALUES ('client_123', 'ChatBot', '1.0.0', 'llm', 'https://api.example.com/chat');
```

### Running an Adversarial Test
1. Create test execution record
2. Call model API
3. Store model output
4. Run safety assessment
5. Record metrics
6. Generate alerts if needed

### Monitoring Model Safety
```sql
SELECT * FROM vw_model_safety_summary 
WHERE risk_level IN ('high', 'critical');
```

### Compliance Reporting
```sql
SELECT * FROM compliance_reports 
WHERE report_period_end >= DATEADD(MONTH, -1, GETUTCDATE())
ORDER BY generated_at DESC;
```

## Security Considerations

1. **API Key Storage**: `api_key_hash` stores hashed API keys, not plaintext
2. **Audit Logging**: All significant actions are logged
3. **Access Control**: Not implemented at DB level - should be handled by application layer
4. **Data Retention**: Consider archival policies for old test data
5. **Sensitive Data**: Model outputs may contain sensitive information - implement appropriate data handling

## Performance Optimization

### Indexes
The schema includes comprehensive indexes on:
- Foreign keys
- Status fields
- Timestamp fields
- Commonly queried combinations

### Partitioning Recommendations
For high-volume deployments, consider partitioning:
- `test_executions` by execution date
- `model_outputs` by creation date
- `audit_logs` by timestamp

### Archival Strategy
Implement regular archival of:
- Test executions older than 6 months
- Audit logs older than 1 year
- Resolved alerts older than 6 months

## Scaling Considerations

### Read Replicas
Use read replicas for:
- Reporting queries
- Analytics
- Dashboard queries

### Write Optimization
- Batch insert test cases when possible
- Use bulk operations for high-volume testing
- Consider queuing for async processing

### Monitoring
Track:
- Database size growth
- Query performance
- Slow queries
- Connection pool usage

## Extension Points

The database is designed to be extensible:

1. **Custom Metrics**: Add new rows to `safety_metrics` for new evaluation criteria
2. **New Attack Types**: Add new test cases and categories as threats evolve
3. **Additional Agents**: Register new AI agents with different capabilities
4. **Custom Reports**: Create new report types in `compliance_reports`
5. **Metadata Fields**: Use JSON fields for custom attributes without schema changes

## Technology Notes

- **Database**: Designed for Microsoft SQL Server (T-SQL syntax)
- **Data Types**: Uses NVARCHAR for Unicode support, DATETIME2 for precision
- **Identity Columns**: Auto-incrementing primary keys
- **Constraints**: CHECK constraints for data validation
- **JSON Support**: Leverages SQL Server JSON functions

## Migration and Deployment

2. Insert initial data for test categories
3. Register system agents
4. Set up monitoring and alerting

- Use migration scripts for updates

- Maintain rollback scripts

3. **Monthly**: Generate compliance reports, archive old data

### Health Checks
- Monitor table sizes
